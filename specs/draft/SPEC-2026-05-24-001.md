# BaseEnv 分離 + LightsOutEnv 実装（パズル拡張基盤の確立）

## 1. 目的・動機

現在 `envs/hanoi_env.py` に `BaseEnv`（抽象基底）と `TowerOfHanoiEnv`（具象）が同居しており、
かつ `BaseEnv` にはハノイ固有のロジック（`_compute_V`, `LAMBDA_*`, `_state_to_key` 等）が混入している。

本 SPEC では以下の 3 点を一括して実施し、**パズル追加コストをゼロに近づける基盤**を確立する。

1. `envs/base_env.py` を新規作成し、パズル共通の最小契約のみを定義する
2. `envs/hanoi_env.py` をリファクタリングして `TowerOfHanoiEnv` のみに整理する
3. `envs/lights_out_env.py` を新規実装し、2 つ目の具象パズルとして Lights Out を追加する

設計方針：**解析スクリプト（`analysis/`）はパズルに依存しない**（`summary.json` を読むだけ）。
`runners/run_local.py` は別 SPEC-2026-05-24-002 で env 非依存化する。

## 2. 物理的要件【physics-agent レビュー案】

### 2.1 `BaseEnv` 抽象インターフェースの物理的妥当性

**審査日**: 2026-05-24（本 SPEC の前段として今会話内で physics-agent 審査済み）  
**判定**: 条件付き合格 → 本 SPEC で全条件解消

#### 確定した設計変更（physics-agent 指摘対応）

| 変更内容 | 理由 |
|---|---|
| `_compute_V` を BaseEnv から削除 | $V(x)$ の定義はパズル間で物理的に非同型。共通基底に置くと比較不能なスケールが混在し研究の根幹を汚染する |
| `LAMBDA_DIST`, `LAMBDA_PENALTY` を `TowerOfHanoiEnv` に移動 | ハノイの $V \in [0,1]$ 正規化に固有の経験値。全パズル共通の物理量ではない |
| `_min_moves_from` を `TowerOfHanoiEnv` に移動 | ハノイ固有の再帰計算。各パズルが独自に `min_moves_from` を実装する |
| `_get_state_coord` を `TowerOfHanoiEnv` に移動 | 座標空間の次元・意味がパズル依存（ハノイ: 3N 次元 one-hot） |
| `_state_to_key(state: dict)` を削除し `state_to_key(state) -> Hashable` として abstract 化 | dict の A/B/C キーはハノイ固有。型を汎用化する |
| `min_moves` を abstract property 化 | `0` 初期値では `_compute_V` でゼロ除算トラップ。ABC による実装漏れ検出のため |
| `extract_moves_from_text` を abstract 化（デフォルト `return []` を廃止） | 実装漏れが accuracy=0 のサイレントバグを生む |
| `get_bad_move` を BaseEnv の abstract から除去 | 現在呼び出し箇所ゼロ（YAGNI）。`TowerOfHanoiEnv` に具体実装として残す |

#### `V(x)` と統計力学的ハミルトニアン $\mathcal{H}(h)$ の分離

- `evaluate_state` が返す $V(x)$ は「**手の評価関数**」（Puzzle 空間の距離代理）
- 統計力学的ハミルトニアン $\mathcal{H}(h)$ は LLM 隠れ状態 $h$ から別途構成する（H3/H4）
- 両者を混同しないこと。$V(x) \neq \mathcal{H}(h)$

### 2.2 LightsOutEnv の $V(x)$ 設計

**審査日**: 2026-05-24（physics-agent 審査済み）  
**判定**: 条件付き合格（user 判断事項 3 件あり）

#### 確定した設計方針

**$V(x)$ の物理的位置づけ**：

$V(x)$ は「**Puzzle 空間上の進捗指標 (progress metric)**」である。ハノイの $V$ と異なり、「エネルギー地形」ではなく純粋な距離関数として機能する（Lights Out に局所最小値・鞍点なし）。

$$
V(x) = \frac{D_{\mathrm{GF2}}(s,\, \text{goal})}{N^2}
$$

ここで $D_{\mathrm{GF2}}(s, \text{goal})$ は GF(2) 線形系 $A\mathbf{x}=\mathbf{b}$ の最小ハミング重み解 $|\mathbf{x}|_1$。  
分母 $N^2$（全セル数）により $V \in [0, 1]$ が厳密に保証される（**user 確定 2026-05-24**）。

**ハノイ $V$ との性質差（確定）**：

| 項目 | ハノイ $V_{\text{Hanoi}}$ | Lights Out $V_{\text{LO}}$ |
|---|---|---|
| 位置づけ | 推論ポテンシャル（エネルギー地形） | 進捗指標（距離関数） |
| 距離の種類 | 非線形再帰距離（ペグ配置コスト） | GF(2) アフィン空間ハミング距離 |
| 局所最小値 | 存在する（SG 相の landscape 起源） | **なし**（affine 空間上の代数的距離） |
| 操作の involution | なし（A→B≠B→A） | あり（同セルを 2 回トグル = 元に戻る） |
| 違法手 | あり（$V>1$ のペナルティ） | なし（全トグルが合法） |

**$V > 1$ の可能性（physics-agent 指摘・確定）**：

GF(2) affine 空間の性質上、合法手のみで $D_{\mathrm{GF2}}(s_t, \text{goal}) > D_{\mathrm{GF2}}(s_0, \text{goal})$ が発生しうる。  
すなわち **$V > 1.0$ は合法手のみで起こりえる**（ハノイと異なり違法手ではない）。  
分母の選択（**user 判断事項①**）によりこの問題の扱いが変わる。

#### H3 コントロール実験としての位置づけ（確定）

**H3**「SG 相の起源は puzzle の landscape ではなく LLM 内部の推論バイアスにある」の  
**falsifiable テスト**として Lights Out を使う論理構造：

| landscape の有無 | H3 が正しい場合 | H3 が偽の場合 |
|---|---|---|
| ハノイ（landscape あり） | SG 相観測 | SG 相観測 |
| Lights Out（landscape なし） | **SG 相観測**（LLM 内部起源） | **SG 相消失**（landscape 起源） |

この構造は falsifiable であり、コントロール実験として物理的に意義がある。

**Involution の注意点（確定）**：

Lights Out のトグルは involution（$X^2 = I$）であるため、同セル 2 連打が：
- 「文法的ループ」（Algorithm C の意味でのループ）
- かつ「物理的に GF(2) 上で意味のある操作（元の状態に戻る）」

の両方を満たす。これにより**Algorithm C（ループ検出）が SG 相シグナルとして使用不可**である理由は「正規表現の非対応」ではなく「**物理的に involution があるためループ検出が意味を持たない**」ことが本質。  
→ SPEC-2026-05-24-002 Section 2 の記述も同旨に修正予定。

**P(q) の定義（確定）**：

Lights Out では puzzle 空間が flat（局所最小値なし）なため、$P(q)$ の双峰性は puzzle 空間ではなく  
**LLM 隠れ状態空間 $h$ または move sequence 空間**で測定する必要がある。  
具体的な $q$ の定義（hidden state 内積 or move-sequence ハミング）は別途壁打ちで確定する。

#### 確定した設計方針（user 確定 2026-05-24）

**①  $V$ の正規化分母**：$N^2$（全セル数）を採用。$V \in [0, 1]$ が厳密に保証される。  
$V(\text{initial}) = k_0/N^2 < 1$（初期状態が必ずしも $V=1$ にならない点は意図的）。

**② 一意性制約の範囲**：「最小解手数が一意」を採用（緩和）。  
解ベクトルが複数あっても最小手数 $k_0$ が一意であれば使用可能。$N=4,5$ も実験対象に含む。

**③ 実験対象 $N$ の範囲**：$N=3,4,5$（スケーリング込み）。

**④ GF(2) 実装**：`galois` ライブラリを使用（`pip install galois`）。

各 $N$ の $\dim \ker A$（OEIS A159257 で確定、research-agent 2026-05-24）：

| $N$ | $\dim \ker A$ | 解の数 | 解の状況 |
|---|---|---|---|
| 3 | 0 | 1 | 一意解。全初期配置で使用可能 |
| 4 | 4 | 16 | 最小手数一意（緩和条件）で使用可能 |
| 5 | 2 | 4 | 最小手数一意（緩和条件）で使用可能 |

### 2.3 Lights Out の「一意解」保証

本研究の必須制約「**解が一意であること**」を満たすため、初期配置は以下の条件を課す：

**確定方針（user 確定 2026-05-24）**：

- 「最小解手数 $k_0$ が一意に定まる」を制約とする（解ベクトル一意性は不要）
- 「解が存在する」（$\mathbf{b}_0 \in \text{Im}(A)$）は必須
- 初期配置の生成方式：**GF(2) 解ベクトルをランダム選択 → 適用して初期状態を逆算**（一発で解あり保証、無限ループなし）

## 4. アルゴリズム仕様【implementation-agent 設計案】

### 4.1 `envs/base_env.py` — 新規作成

```python
"""
base_env.py — パズル環境の抽象基底クラス

全パズルが継承する最小契約のみを定義する。
V(x) の定義はパズル固有であり、BaseEnv は定義しない。
外部モジュール依存なし（標準ライブラリのみ）。
"""

from abc import ABC, abstractmethod
from typing import Hashable


class BaseEnv(ABC):
    """全パズル共通の抽象基底クラス。

    契約：
      - evaluate_state(moves) -> float : V(x)。V=0.0 がゴール、V=1.0 が初期状態
      - goal_reached(moves) -> bool    : ゴール到達判定
      - min_moves (property) -> int    : 初期状態からの最短手数（正の整数）
    """

    def __init__(self, N: int) -> None:
        self.N = N

    @property
    @abstractmethod
    def min_moves(self) -> int: ...

    @property
    @abstractmethod
    def initial_state(self): ...

    @property
    @abstractmethod
    def goal_state(self): ...

    @abstractmethod
    def get_prompt(self) -> str: ...

    @abstractmethod
    def evaluate_state(self, current_moves: list) -> float: ...

    @abstractmethod
    def goal_reached(self, current_moves: list) -> bool: ...

    @abstractmethod
    def solve(self) -> list: ...

    @abstractmethod
    def extract_moves_from_text(self, text: str) -> list: ...

    @abstractmethod
    def state_to_key(self, state) -> Hashable: ...

    @abstractmethod
    def make_sub_env(self, N: int) -> 'BaseEnv': ...
    """few-shot 例文生成用。同パズル種の小サイズ env を返す。"""
```

**注意点**：

- `initial_state`, `goal_state` を abstract property にすることで、サブクラスでの初期化漏れを ABC が検出できる
- `_get_state_coord`, `_min_moves_from` は BaseEnv から削除（ハノイ・各パズル固有の実装に移す）
- `get_neighbors`, `get_prompt_from_state`, `_simulate_states` は現在外部から未使用（dead code）。`TowerOfHanoiEnv` には残すが BaseEnv の契約には含めない

### 4.5 implementation-agent 設計確認

**確認日**: 2026-05-24  
**担当**: implementation-agent

#### 設計全体の評価

`base_env.py` 分離 + `hanoi_env.py` リファクタリング + `lights_out_env.py` 新規実装という 3 段構成は、単一責任原則・依存性逆転の両面で妥当である。特に `_compute_V`・`LAMBDA_*` の `TowerOfHanoiEnv` への移動と `min_moves` の abstract property 化（ゼロ除算トラップ排除）は設計の整合性を大きく高める。`make_sub_env(N)` の抽象化は few-shot プロンプト生成で必要になる前に契約に含める判断として適切であり、SPEC-B との連結点が明確である。

唯一の設計上の懸念は `initial_state` と `goal_state` を abstract property とする点である。現在の `TowerOfHanoiEnv` はこれらをインスタンス変数として `__init__` 内で設定しており、abstract property として再定義するにはバッキングストアの命名（`_initial_state` / `_goal_state`）を変更する必要があり互換性に注意が必要である。また `_simulate_states` が `self._state_to_key` を呼び出しているが、メソッド名が `state_to_key` にリネームされるため更新漏れがサイレントな `AttributeError` につながるリスクがある。

#### 懸念点・実装時の注意点

#### AbstractMethod 削除による後方互換性への影響

**`_simulate_states` の `_state_to_key` 呼び出し**（最重要）

**`get_bad_move` の abstract 除去**

#### GF(2) 実装の注意点

**`_build_adjacency_matrix`** : $N^2 \times N^2$、`dtype=np.int8`。`np.linalg.solve` は実数体のため使用不可。GF(2) Gaussian elimination は自前実装が必要（または `galois` ライブラリ使用）。

**`_gf2_solve` の実装難度**：

1. 拡大行列 $[A|b]$ を構築
2. 行基本変換（`% 2`）で行階段形に変換し解の存在・一意性を判定
3. 後退代入で解ベクトル取得
4. Nullspace 次元 > 0 の場合、全 coset を列挙して最小ハミング重みを選択

**`galois` ライブラリの利用可否**：GF(2) 演算を完全サポート。依存追加の可否を user に確認することを推奨。自前実装の場合は追加 50〜100 行が必要。
