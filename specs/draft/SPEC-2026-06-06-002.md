# Frog Jump 環境実装 — H7' の L スケーリング検証用

## 1. 目的・動機

**H7'（asymmetric melting）**の核心主張「経路長 L=K(N) が大きくなるほど recitation 窓が縮小・消滅する」を定量的に検証する。

Hanoi では $K(N) = 2^N - 1$（指数増大）なため、N=6（K=63手）で recitation が消滅した。Frog Jump では $K(N) = N(N+2)$（多項式増大）なため：
- 同じ N ではより長い解を持つ（N=4 で K=24 vs Hanoi の K=15）
- より大きな N まで recitation が持続すると H7' が予測する
- L スケーリング則の精密検証：$p_\text{recit}(N) \sim (1-\epsilon)^{N(N+2)}$

また Frog Jump は Hanoi と**同様に正準解が固定**（同一 N では解は常に同じ手順）なため：
- Qwen の recitation が出れば「Hanoi に限らず RLVR 訓練モデルの普遍的性質」を示す
- DeepSeek が recitation を示さなければ $J_\text{mem}$ の訓練依存性を確認
- Lights Out で Qwen が memorize した場合：H7' の generality 強化のためにこの SPEC を優先採択

## 2. 物理的要件【physics-agent 担当】

### 2.1 保存則・対称性の要件

- **一意な解の存在**：N 枚ずつのカエル（L 型・R 型）の交換問題。最短解は一意（Hanoi 同様に正準手順が一つだけ存在）。
- **初期・目標状態の対称性**：`[L×N, _, R×N]` → `[R×N, _, L×N]`。目標状態は初期状態の鏡像。B/C ペグ対称性に相当する左右対称性が存在。
- **合法手の規則**：(1) カエルが1マス前進（空きマスへ）、(2) カエルが反対色の1匹を跳び越す（ちょうど2マス前進）のみ。後退・2マス以上のジャンプは不合法。

### 2.2 極限値チェック項目

- **T→0**：Reasoning-ordered。LLM が最短解（K=N(N+2) 手）を出力。
- **T→∞**：PM。カエルが動かなくなるか、不合法な手を出し続ける。
- **N=1**：K=3手（極小、LLM が容易に解ける）。Ordered 相の T 耐性が高い。
- **N=6**：K=48手（Hanoi N=6 の K=63 より短い）。H7' では recitation が持続するはず。
- **recitation 窓の N 依存性**：$p_\text{recit}$ のピーク温度は N に依存しないはず（H7' の基本予測）。窓の幅（高温側の消滅）が $\sim(1-\epsilon)^{N(N+2)}$ で決まる。

### 2.3 スピングラス・Hopfield・RSB との整合性

- **oscillatory レジーム**：カエルが同じ方向に動いた後、逆方向に戻る「往復ループ」が自然な失敗モード。move_loop_repeat として検出可能（状態ハッシュで）。
- **Hanoi との対応**：`src_position → dst_position` の移動記録は Hanoi の `(src_peg, dst_peg)` と同型。既存の loop detection ロジック（Algorithm C）がほぼそのまま流用可能。
- **K(N) スケーリング則の検証**：$p_\text{recit}(N) \propto e^{-\alpha N(N+2)}$ の形で fitting できるか。Hanoi では $e^{-\alpha(2^N-1)}$ に相当。指数 vs 多項式の差が L スケーリング則の核心。

### 2.4 懸念点・要確認（物理）

- Frog Jump は正準解が固定なので Qwen が memorize する可能性は Hanoi と同程度。Lights Out が「memorize しない」ことを示した場合、このパズルでも memorize しないかもしれない。その場合は N-puzzle（SPEC-001）の方が H7' の generality テストに適する。
- 往復ループの「戻る」方向が L 型か R 型かで loop の物理的意味が変わる。loop detection のロジックは `(position_before, position_after)` のペアで一意に track できるか要確認。
- Hanoi の $J_\text{mem}$ 起動が「正準 Hanoi 手順を見た」ことで条件付けられているなら、Frog Jump では別の `anchor` が必要。訓練データに Frog Jump の正準解が含まれているかは不明。

## 4. アルゴリズム仕様【implementation-agent 担当】

### 4.1 擬似コード / フロー

```
class FrogJumpEnv(BaseEnv):
    N: int        # 片側のカエルの数
    board: list   # 長さ 2N+1 の配列。値: 'L', 'R', '_'
    visited: set  # 訪問済み状態ハッシュ（loop detection 用）

    初期状態: ['L'] * N + ['_'] + ['R'] * N
    目標状態: ['R'] * N + ['_'] + ['L'] * N
    K(N) = N * (N + 2)

    reset():
        board = ['L'] * N + ['_'] + ['R'] * N
        visited = {state_hash(board)}

    state_hash(board) -> tuple:
        return tuple(board)

    initial_prompt() -> str:
        """
        現在の盤面を表示。
        例（N=3）:
          [L L L _ R R R]  (位置: 0 1 2 3 4 5 6)
        L は左カエル（右方向にのみ進む）
        R は右カエル（左方向にのみ進む）
        """

    apply_move(from_pos: int) -> (new_board, valid, loop):
        """
        from_pos にいるカエルを合法的な位置へ移動。
        合法手:
          L カエル: from_pos+1 が '_' → from_pos+1 へ（1マス前進）
                    from_pos+2 が '_' かつ from_pos+1 が 'R' → from_pos+2 へ（ジャンプ）
          R カエル: from_pos-1 が '_' → from_pos-1 へ（1マス前進）
                    from_pos-2 が '_' かつ from_pos-1 が 'L' → from_pos-2 へ（ジャンプ）
        """
        find empty_pos (where board == '_')
        frog_type = board[from_pos]
        valid = check_legality(from_pos, frog_type, empty_pos)
        if not valid: return (board, False, False)
        new_board = move(board, from_pos)
        h = state_hash(new_board)
        loop = h in visited
        visited.add(h)
        return (new_board, True, loop)

    is_goal() -> bool:
        return board == ['R'] * N + ['_'] + ['L'] * N

    evaluate_state() -> float:
        """
        V(x) = 合計変位 / K(N) ∈ [0,1]
        各カエルの目標位置までの距離の和を正規化。
        V=0 がゴール、V=1 が初期状態。
        """
        total = sum(
            |current_pos(frog_i) - goal_pos(frog_i)|
            for each frog
        )
        return total / (2 * N * (N + 1))  # 最大変位で正規化
```

**LLM への出力形式**：
- LLM に「位置 X のカエルを移動する」と出力させる
- 正規表現: `move\s+(?:frog\s+(?:at\s+)?)?(?:position\s+)?(\d+)`
- 出力例: "Move frog at position 2", "Move position 0", "Move 3"

**loop detection**：
- Hanoi の `check_early_stop`（Algorithm C）をほぼそのまま流用
- `state_hash = tuple(board)` で位置状態をハッシュ化
- 同一状態が再現 → `early_stop='move_loop_repeat'`

### 4.2 既存コードとの接続点

- `envs/base_env.py`：`BaseEnv` を継承
- `runners/run_local.py`：`--puzzle frog_jump` フラグで切替
- `runners/run.py`：`check_early_stop`（Algorithm C）がそのまま使用可能
  - `_MOVE_RE` の定義を frog_jump 用に追加（`from_pos` の正規表現）
- 新規ファイル：`envs/frog_jump_env.py`

### 4.3 設計上の制約・注意事項

- `move_ceiling` 設定：K(N)×3 を推奨（N=3 なら 45 手、N=6 なら 144 手）。
- L カエルは右方向のみ、R カエルは左方向のみ合法。逆方向への移動は `valid=False` として`no_move_catchall` ではなく違反手として処理（v_score > 1 を設定）。
- プロンプト設計：各カエルの「進める方向」を明示することで LLM の混乱を防ぐ。
- Hanoi の `_MOVE_RE_WITH_DISK` に相当するものとして、`_MOVE_RE` の位置引数は `(from_pos, frog_type)` のペアで loop 判定。
