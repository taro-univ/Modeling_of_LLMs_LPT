# run_local.py の env 非依存化（パズル横断実験の実行基盤）

## 1. 目的・動機

現在 `runners/run_local.py` は `TowerOfHanoiEnv` を直接生成しており、Lights Out 等の新規パズルで
実験を走らせるには `run_local.py` の大幅な書き換えが必要になる。

本 SPEC では `run_local.py` の実験ロジックを `env: BaseEnv` を受け取る形に変更し、
**パズルを切り替えるだけで同じランナーが動く設計**にする。

**前提**：SPEC-2026-05-24-001 が実装済みであること（`BaseEnv`, `TowerOfHanoiEnv`, `LightsOutEnv` が確立済み）。

**不変の制約**：
- 早期終了ロジック（`run.py` の `EarlyStopConfig`, `check_early_stop`）は**変更しない**
- 隠れ状態キャプチャ（`make_capture_layers`, npz 書き出し）は**変更しない**
- 既存の `run_full_sweep.sh` でハノイ実験が変わらず動くこと

---

## 2. 物理的要件【physics-agent レビュー案】

本 SPEC は純粋なインフラリファクタリングであり、物理的な計算ロジックを変更しない。

確認事項（軽微）：

- `check_early_stop` は `accumulated_text` のパターンマッチングで動作し、env に依存しない  
  → Lights Out 実験でも同じ早期終了判定が走ることの物理的含意を理解したうえで使用する

**Algorithm C 不適用の理由（physics-agent 確認済み 2026-05-24）**：

Lights Out で Algorithm C（ループ検出）が機能しない理由は、「正規表現が "Toggle (i,j)" に対応しないから」ではなく、**物理的に involution があるため SG シグナルとして使用不可**であることが本質。

- Lights Out のトグル操作は involution（$X^2 = I$）：同セル 2 連打が「文法的ループ」かつ「GF(2) 上で意味のある操作（元に戻る）」を同時に満たす
- そのため「ループ」と「意図的な反転操作」が区別不能になり、Algorithm C のシグナルが SG 相の指標として信頼できない
- **SG 相の検出は P(q) 解析（hidden state 空間 or move sequence 空間）で行う**（SPEC-001 Section 2.2 参照）

**結論**：Lights Out では Algorithm C を無効化して実験する。P(q) ベースの SG 判定に切り替える。この変更は本 SPEC の実装範囲外（`check_early_stop` は変更しない）。実験時に明示的に `--no-early-stop` または Algorithm C 判定を無視する運用で対応。

### 4.3 Known Limitation：`build_few_shot_messages` の Lights Out 非対応

`build_few_shot_messages` は現在ハノイ専用の `SYSTEM_HINT` と few-shot 構築ロジックを持つ。
`env.make_sub_env(ex_n)` への置換後も、LightsOut を渡した場合はハノイ用プロンプトが生成される。

**本 SPEC の対応**：`env.make_sub_env(ex_n)` への型シグネチャ変更のみ実施。
コードに以下のコメントを追加する：

```python
# TODO(SPEC-FUTURE): build_few_shot_messages はハノイ専用プロンプトを使用。
# LightsOutEnv 対応は別 SPEC で BaseEnv.get_few_shot_examples() 等を追加して対応予定。
```

Lights Out の実験では `--n-shot 0` で few-shot を無効化して運用する（暫定）。

設計全体の評価
--------------
本 SPEC の変更範囲は run_local.py への局所的な差し替えのみであり、早期終了ロジック・隠れ状態
キャプチャ・出力パス生成のいずれにも触れない。SPEC-2026-05-24-001 が確立した BaseEnv 抽象を
利用して型アノテーションと生成箇所を差し替えるだけなので、実装リスクは低い。

後方互換性については `--puzzle` のデフォルト値を `hanoi` にする設計で既存コマンドが変更なしで
動作する点を実際のコードと照合して確認した。ただし後述の通り、変更が必要な箇所が仕様書に
掲載された行番号・関数名と一部ずれているため、実装前に要注意ポイントとして整理する。

変更箇所の行番号確認
--------------------
以下、run_local.py の実際の行番号と仕様書の記述を照合した結果。

(1) import の変更（仕様書: Line 28）
  実際 Line 28: `from envs.hanoi_env import TowerOfHanoiEnv`  → 行番号は一致。
  ただし変更後は `from envs.base_env import BaseEnv` に加え、
  `from envs.hanoi_env import TowerOfHanoiEnv` と
  `from envs.lights_out_env import LightsOutEnv` を両方追加する必要がある。
  `TowerOfHanoiEnv` は puzzle_factories の値として main() で依然必要。
  仕様書の「Before/After」は BaseEnv だけに置き換えるように読めるが、
  TowerOfHanoiEnv と LightsOutEnv の import も残す（追加する）形が正しい。

(2) build_few_shot_messages のシグネチャ変更（仕様書: Line 95）
  実際 Line 95: `def build_few_shot_messages(env: TowerOfHanoiEnv, n_shot: int)` → 行番号は一致。

(3) build_few_shot_messages 内の TowerOfHanoiEnv(N=ex_n) 呼び出し（仕様書: Line 117）
  実際 Line 117: `ex_env = TowerOfHanoiEnv(N=ex_n)` → 行番号は一致。
  `env.make_sub_env(ex_n)` への置換は安全。BaseEnv.make_sub_env は abstract メソッドで
  あり、TowerOfHanoiEnv も LightsOutEnv も実装済みであることを envs ディレクトリで確認済み。
  LightsOutEnv.make_sub_env は `LightsOutEnv(N, seed=42)` を返す（lights_out_env.py Line 59-60）。
  ただし build_few_shot_messages は現在ハノイ専用の SYSTEM_HINT を使って few-shot を構築している。
  LightsOutEnv を渡した場合、few-shot メッセージの内容もハノイのものになり、不適切なプロンプトが
  生成される。この問題は Section 4.2「将来対応」として明示されているが、実装時に混乱を招く可能性が
  あるため注意を要する（懸念点 1 を参照）。

(4) 型アノテーション変更（仕様書: Lines 220, 382, 424）
  実際の該当行を確認すると：
  - Line 220: `env: TowerOfHanoiEnv` （_prepare_input_ids の引数）

  - Line 424: `env: TowerOfHanoiEnv` （generate_with_hidden_states の引数）

(5) run_experiment_hf 内の env 生成（仕様書: Line 591）
  実際 Line 591: `env = TowerOfHanoiEnv(N=N)` → 行番号は一致。
  ただし run_experiment_hf のシグネチャも変更が必要になる（懸念点 2 を参照）。

  parse_args() は Line 702 から始まる。`--puzzle` 引数と puzzle_factories を
  main() または parse_args() 後の処理として追加する。
  この箇所は仕様書に具体的な行番号が示されていないが、
  parse_args() の末尾（現 Line 741 の return 直前）に追加するのが自然。

懸念点・実装時の注意点
----------------------
番号 | 優先度 | 内容

1 | 高 | build_few_shot_messages がハノイ固有の SYSTEM_HINT と TowerOfHanoiEnv ベースの
       few-shot 構築ロジックを持っている。`env.make_sub_env(ex_n)` への置換だけでは
       LightsOutEnv を渡した際にハノイ用のプロンプトが生成される。
       SPEC-002 のスコープは「インフラリファクタリング」で few-shot 内容の変更は
       含まないと読めるが、LightsOutEnv で実際に実験できる状態にするには
       build_few_shot_messages か SYSTEM_HINT も env 依存に改変する必要がある。
       今回スコープ外なら、LightsOutEnv への対応は別 SPEC として切り出す方が安全。
       実装時には「LightsOutEnv を渡すと few-shot がハノイ用になる」という Known Limitation を
       コメントか README に明記することを推奨する。

2 | 高 | run_experiment_hf（Line 561）は env を内部で `TowerOfHanoiEnv(N=N)` として生成しており
       （Line 591）、関数シグネチャに env パラメータが存在しない。
       仕様書 Section 4.1 の「Line 591: env 生成をファクトリ経由に変更」は
       `env = env_factory(N)` への置換を指しているが、env_factory を受け渡す経路が不明確。
       選択肢は 2 つ：
       (a) run_experiment_hf の引数に `env_factory: type` を追加して内部で `env_factory(N)` を呼ぶ
       (b) run_experiment_hf の引数に `env: BaseEnv` を追加して外から渡す
       (b) の方が単一責任に合致する（env の生成責務を main に集約）。
       どちらを採用するか Codex に委ねると設計が揺れる可能性があるため、仕様書に明記を推奨する。

3 | 中 | _resolve_output_paths（Line 760-776）と _write_meta_json（Line 779-799）は
       出力パスとメタデータの `environment` フィールドに `"hanoi"` がハードコードされている
       （Line 793: `"environment": "hanoi"`）。
       `--puzzle` を追加した後、`environment` フィールドも `args.puzzle` で上書きする必要がある。
       また出力先パスも `results/hanoi/...` にハードコードされているため（Line 770）、
       `results/{args.puzzle}/...` に変更しないとパズル種が混在したディレクトリになる。
       仕様書 Section 4.2 では「将来対応」とされているが、`environment` フィールドの変更は
       DB sync にも影響するため扱いを明確にしておく必要がある。

4 | 低 | LightsOutEnv(N=3) の初期化（seed=None 時）は内部でランダム初期状態を生成する
       （lights_out_env.py の _generate_initial_state）。seed を指定しないと
       同じ N でも実行ごとに初期盤面が変わる。
       実験の再現性のため `--seed` 引数の追加か、LightsOutEnv の初期状態固定方針を
       別途検討する必要がある。今回スコープ外で構わないが将来 SPEC として残すべき論点。

5 | 低 | generate_with_hidden_states（Line 418）の docstring にある Args リストには
       `env` の説明が存在しない。型アノテーション変更と合わせて docstring も
       `env: BaseEnv` に更新することを推奨する。
