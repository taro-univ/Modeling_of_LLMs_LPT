# N-puzzle（スライドパズル）環境実装 — 普遍 H_eff 取得用

## 1. 目的・動機

**普遍 H_eff = -∇V(h) + A(h) + √(2T)ξ** を DeepSeek/Qwen 両モデルに対してフィットするためのデータを取得する。

Hanoi は正準解が固定（N=3 で常に同じ7手列）なため、Qwen3 が RLVR 訓練の副産物として解法を記憶（recitation）する。これが普遍 V(h) と A(h) の fitting を妨げる confound になっている。

N-puzzle は**毎試行で異なるランダム初期配置**（seed 指定）を使うため、どのモデルも特定の解法を記憶できない。
→ recitation well（Qwen 固有の $J_\text{mem}$ 項）の寄与がゼロになり、**両モデルで共通の V と A だけを純粋に測定できる**。

期待する観察：
- DeepSeek と Qwen の **reasoning → oscillatory → PM 構造が一致**する（普遍 H_eff の存在を支持）
- move_loop 類似の循環失敗モード（oscillatory レジーム）が両モデルで出現
- Lights Out と異なり `--no-loop-detection` 不要 → oscillatory レジームが行動レベルで検出可能

## 2. 物理的要件【physics-agent 担当】

### 2.1 保存則・対称性の要件

- **一意な目標状態**：タイル昇順配置 [1,2,...,N²-1,0] が唯一のゴール。複数のパスが存在するが、成否判定は目標状態への到達で一意に決まる。
- **可解性保証**：ランダム生成インスタンスは必ず可解であること（偶置換チェック実装）。不可解な初期配置を出力しないこと。
- **行動空間の対称性**：空きマスへの隣接タイルスライド（4方向）のみ。Hanoi の「ペグ間ディスク移動」と異なり、各タイルの識別が重要。

### 2.2 極限値チェック項目

- **T→0**：モデルが最適解を見つけられる場合、goal_reached のみ。Reasoning-ordered レジーム。
- **T→∞**：ランダムなタイル移動 → no_move_catchall または move_ceiling。PM レジーム。
- **N=3（8-puzzle）**：平均最短手数 ~22。小さいため LLM が推論可能な場合がある。
- **N=4（15-puzzle）**：平均最短手数 ~52。ほとんどのモデルで困難。oscillatory と PM が支配的になるはず。
- **N=5（24-puzzle）**：平均最短手数 ~100+。ほぼ全試行が失敗 → N 上限として使用。

### 2.3 スピングラス・Hopfield・RSB との整合性

- **loop detection あり**：同一盤面状態の再訪 = `move_loop_repeat`。oscillatory レジーム（A(h) 成分）が行動レベルで観測可能。
- **seed varying の物理的意味**：各試行が独立したランダムインスタンス → $J_\text{mem} = 0$ の条件下での純粋な $(V, A)$ 測定。recitation の自由エネルギー勾配が存在しない系。
- **V(x) の定義**：$V(x) = D(x, x_\text{goal}) / K(N)$。$D$ はマンハッタン距離またはタイルの不整合数で代替可（Hanoi と同様の[0,1]正規化）。

### 2.4 懸念点・要確認（物理）

- seed varying により各試行の目標がポテンシャル地形上の**異なる点**に対応する。Hanoi では全試行の目標が同一。この「ゴールの揺らぎ」が P(q) 解析に与える影響を要確認。
- 15-puzzle の最短手数は NP-hard（IDA*）で算出。実行時に毎回計算するか、十分な手数制限（move_ceiling）で代用するかを決める。
- V(x) にマンハッタン距離を使う場合、これは下限評価（admissible heuristic）であり真の最短距離ではない。物理的解釈への影響を要確認。

## 4. アルゴリズム仕様【implementation-agent 担当】

### 4.1 擬似コード / フロー

```
class NPuzzleEnv(BaseEnv):
    N: int          # グリッドサイズ (3=8-puzzle, 4=15-puzzle)
    seed: int       # ランダム初期配置のシード
    grid: np.array  # N×N の現在盤面（0=空きマス）
    visited: set    # 訪問済み盤面ハッシュ（loop detection 用）

    reset(seed):
        grid = generate_solvable_random(N, seed)
        visited = {state_hash(grid)}
        return initial_prompt()

    initial_prompt() -> str:
        """
        現在の N×N グリッドを文字列で表示。
        例（N=3）:
          8 1 3
          4 _ 2
          7 6 5
        空きマスは '_'。隣接タイルを空きマスへ移動して昇順を目指す。
        """

    apply_move(tile_number: int) -> (new_grid, valid, loop):
        """
        tile_number のタイルを空きマス方向にスライドする。
        valid: タイルが空きマスに隣接しているか
        loop: state_hash(new_grid) が visited に存在するか
        """
        find empty_pos
        find tile_pos of tile_number
        check adjacency（4方向）
        if not adjacent: return (grid, False, False)
        new_grid = slide(grid, tile_pos, empty_pos)
        h = state_hash(new_grid)
        loop = h in visited
        visited.add(h)
        return (new_grid, True, loop)

    is_goal() -> bool:
        return grid == [[1,2,...,N-1], ..., [..., N²-1, 0]]

    evaluate_state() -> float:
        """V(x) = 不整合タイル数 / (N²-1)  ∈ [0,1]"""
        misplaced = sum(1 for i,j where grid[i][j] != goal[i][j] and grid[i][j] != 0)
        return misplaced / (N*N - 1)

    generate_solvable_random(N, seed):
        """
        可解なランダム置換を生成。
        偶置換チェック：
          N が奇数（3,5,...）: 転倒数が偶数なら可解
          N が偶数（4,...）: 転倒数 + 空きマスの行（下から）が偶数なら可解
        可解でなければ任意の2タイルをスワップして修正。
        """
```

**LLM への移動指示の parse**：
- LLM に「タイル番号 X を移動する」と出力させる
- 正規表現: `move\s+(?:tile\s+)?(\d+)` または `slide\s+(\d+)`
- 出力例: "Move tile 6", "Slide 3", "Move 3 to empty space"

**loop detection の実装**：
- `state_hash = tuple(grid.flatten())`（タプルはハッシュ可能）
- visited は set で O(1) ルックアップ
- Hanoi の `_MOVE_RE` に相当する位置で呼ぶ

### 4.2 既存コードとの接続点

- `envs/base_env.py`：`BaseEnv` を継承
- `envs/hanoi_env.py`：`evaluate_state()` の設計を参考
- `runners/run_local.py`：`--puzzle` フラグで切替済み（`--puzzle n_puzzle`）
- `runners/run.py`：`EarlyStopConfig` の `check_early_stop` をそのまま使用。loop detection の判定は env 側で行い、`early_stop='move_loop_repeat'` を返す。
- 新規ファイル：`envs/n_puzzle_env.py`

### 4.3 設計上の制約・注意事項

- `generate_solvable_random` は可解性保証が必須。不可解なインスタンスを渡すと永遠に解けない。
- `move_ceiling` の設定：最短解の3–5倍を推奨（N=3 なら 100 手、N=4 なら 200 手）。
- LLM の出力が「どのタイルを動かすか」なのか「空きマスをどの方向に動かすか」なのかをプロンプトで明確に指定すること。タイル番号指定の方が parse が単純。
- `--no-loop-detection` フラグは**使わない**（N-puzzle では有効な loop detection が可能）。
