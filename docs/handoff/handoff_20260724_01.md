3. 探索フェーズと最終回答フェーズを分ける prompt / parser を入れる。
   - 目的:
     - LLM-only の経路探索は維持する。
     - ただし、探索中の候補手と最終提出手順を評価上は分離する。
   - prompt案:
     ```text
     You may reason freely in the search phase.
     Do not put the final move sequence anywhere except inside <final>...</final>.
     Only moves inside <final> will be graded.

     After searching, output:
     <final>
     Flip k
     Flip k
     ...
     </final>
     ```
   - debug/run側の採点案:
     - `moves_all_mentions`: 生成全文から抽出した全 `Flip k`
     - `moves_final`: `<final>...</final>` 内だけから抽出した `Flip k`
     - `goal_reached_during_search`: `moves_all_mentions` の軌道が一度でも goal を通過したか
     - `final_accuracy`: `moves_final` で goal に到達したか
     - `accuracy` は互換性のため当面残すが、Pancake の主指標は `final_accuracy` に移す。
   - hidden解析での扱い:
     - `all_mentions_trajectory`: 探索軌道。思考中の候補・却下手も含む。
     - `final_answer_trajectory`: 提出解の軌道。正答率・V(x) の主対象。
     - `<final>` 開始 token 付近を decision / commit phase としてラベル化する。
   - この方式は外部 simulator や BFS が探索を肩代わりしないため、LLM-only の研究目的を壊さない。
   - モジュール分割は主実験ではなく、原因切り分け用 control として扱う。

## 4. 未解決の論点・注意

- Pancakeの評価は2系統に分ける必要がある。
  - `final answer trajectory`: 正答率用。`<final>...</final>` 内だけを採点する方式を優先。
  - `reasoning search trajectory`: reasoning中の全 `Flip k` mention。探索過程モデリング用。
- 現行の `extract_moves_from_text()` は生成本文中の全 `Flip k` を拾う。
  - 正答率だけを見ると過大評価になり得る。
  - 一方で探索軌道解析には有用。
- 二段階 prompt の導入後も、LLM-only と control を混同しない。
  - 主実験: LLM が探索・検証・最終提出をすべて行う。
  - control: deterministic simulator / legal move feedback / distance feedback / BFS oracle を段階的に追加し、状態追跡ミス・探索方針ミス・停止制御ミスを分解する。
- Pancakeでは `no_move_catchall` が早すぎる可能性が高い。
  - `--no-early-stop` でPASSしたため、モデルは最終的には `Flip k` を出せる。
  - early_stop調整は次以降の別タスク。
- hidden state保存は次タスクではscope外。
  - まずdebug sweepと探索軌道解析で、何を正解・軌道として扱うか決める。
- `debug_prompt.py` はデバッグ用。大規模本実験は `run_local.py`。
