## 2. 新しい中心仮説

### 2.1 仮説の文章表現

Transformer の layer 方向の発展は、モデルアーキテクチャと prefix 状態によって規定される離散的な内部制約である。一方、token 方向の hidden-state dynamics は自己回帰的な外部時間発展であり、その drift、Move event response、diffusion は問題複雑度

```text
c_i = (N_i, m_i),  m_i = initial min_moves
```

に依存する。

現在の N=3 success 軌道は `c=(3,3)` の局所系における1標本として扱う。複雑度を固定した局所系から始め、複数の `N` / `min_moves` 条件へ拡張して複雑度依存を検証する。

この1軌道を、まだ「N=3成功の典型的な型」や1つの regime とは呼ばない。同じ条件でも sampling によって軌道は変わるため、複数試行から少なくとも次を分離し、同条件内の再現性が確認できて初めて成功軌道の型を議論する。

- 1試行内の token 時間変動
- 同じ `N` / `min_moves` / outcome における試行間変動
- 同じ複雑度における成功と失敗の差
- `N` または `min_moves` を変えたときの条件間変動

したがって現在の1軌道から得られたのは、方程式を推定するための標本集合ではなく、方程式の候補と必要な観測量を考えるための具体例である。

### 2.2 layer 方向: 離散的な内部制約

layer は連続時間ではなく Transformer block の離散列なので、差分写像として扱う。

Transformer の推論計算は、token を外側の時間ループ、layer を各 token 内部の離散的な計算列とする二重構造を持つ。

```text
token t:    low -> ... -> mid -> ... -> top -> tokenを出力
                                                   |
                                                   v
token t+1:  low -> ... -> mid -> ... -> top -> tokenを出力
```

この構造から、layer 方向を token 方向と同じ連続時間の細分として扱わず、各 Transformer block が課す内部写像または制約として扱う。

```text
h[t,l+1] = h[t,l] + F_l(h[t,l], K[<=t,l], V[<=t,l])
```

または制約式として、

```text
R_l(t)
  = h[t,l+1] - h[t,l]
    - F_l(h[t,l], K[<=t,l], V[<=t,l])
  = 0
```

と書く。

`h[t,l]` だけでは attention が参照する過去 token の key/value を含まないため、厳密には Markov 状態ではない。`F_l(h[t,l])` とだけ書く場合は、prefix / KV cache の効果を hidden に粗視化した有効近似であることを明記する。

### 2.3 token 方向: 複雑度依存の外部時間発展

layer 制約 `R_l(t)=0` のもとで、token 方向には次の有効方程式を考える。

```text
Delta_t h_i[t,l]
  = G_l(h_i[t,l], phi_i[t]; c_i, T)
    + J_l(e_i[t], q_i[t]; c_i)
    + epsilon_i[t,l]
```

記号の役割:

- `i`: trial
- `c_i=(N_i,m_i)`: trial 全体で固定された複雑度。`m_i` は初期状態の `min_moves`
- `T`: sampling temperature。複雑度とは分ける
- `phi_i[t]`: reasoning / verification / final commit などの phase
- `e_i[t]`: Move mention などの event
- `q_i[t]`: candidate state、動的な distance-to-goal など、token ごとに変わる状態
- `G_l`: 通常時の token drift
- `J_l`: event 近傍の追加的な応答
- `epsilon_i[t,l]`: 未観測 prefix 状態、sampling、粗視化に由来する有効ノイズ

初期 `min_moves=m_i` は固定パラメータ、candidate state の distance は動的変数であり、同じ変数として扱わない。

| 量 | 役割 | 時間依存性 |
|---|---|---|
| `N_i` | stack長、状態表現長、合法手候補数などに関係するtrial-level条件 | trial内で固定 |
| `m_i = min_moves(initial_state_i)` | 初期状態からgoalまでの厳密な最短計画長 | trial内で固定 |
| `q_i[t]` | reasoning中に言及されたcandidate stateなど | tokenごとに変化 |
| `d_i[t]` | candidate stateからgoalまでの動的distance | tokenごとに変化 |

特に `m_i=3` だけでは、reasoning途中の候補状態がgoalへ近づいているか、逆行しているかを表せない。初期複雑度 `m_i` と動的distance `d_i[t]` は別の説明変数として保持する。

### 2.4 仮説の境界

- 最初から `N` と `min_moves` を1つの複雑度スカラーへ潰さず、`c=(N,min_moves)` のベクトルとして扱う。
- layer 側が複雑度非依存であることは前提ではなく、まず検証対象とする。
- layer update の残差が `N` / `min_moves` に系統依存するなら、仮説を

  ```text
  F_l = F_l(...; c)
  ```

  へ修正する。
- hidden のみを使う式は有効力学であり、attention / MLP / KV を含む厳密な機構式とは区別する。

## 3. 反証可能な検証予測

1. 同じ `N` / `min_moves` の成功試行では、token drift、Move event response、phase ごとの軌道に一定の試行間再現性がある。
2. `min_moves` を揃えて `N` を変えた場合にも token dynamics が系統的に変わるなら、計画長だけでなく状態表現長や合法手候補数が `G_l` に影響している。
3. `N` を揃えて `min_moves` を変え、長い計画ほど滞留時間、逆行 event、diffusion が増えるなら、計画長が token dynamics の制御パラメータになっている。
4. `c=(N,min_moves)` を入力しない token 発展モデルより、`G_l(...;c)` の方が held-out trial の次時点 hidden をよく予測する。
5. layer 写像 `F_l` が複雑度をまたいで比較的よく転移し、token 写像 `G_l` の方に強い複雑度依存が現れるなら、中心仮説を支持する。
6. 反対に、layer update の予測残差が `N` / `min_moves` とともに系統変化するなら、「複雑度は token 方程式だけに入る」という強い形は棄却し、`F_l(...;c)` へ拡張する。

予測モデルを比較するときは token row を独立標本と数えず、trial 単位で train / validation / test を分割する。同一軌道内の多数 token は強く相関している。

## 4. 必要なデータ取得方針

### 4.1 なぜ token:1 が必要か

- `token:8` では Move event が保存点の間に入り、最大7 token 遅れた hidden rowへ対応する。
- `Flip 2` のようなevent自体が複数subword tokenにまたがりうる。
- impulse の開始、最大変化、緩和を区別するには generated 区間を `token:1` で保存する必要がある。
- eventに対する因果順序を読むため、hidden rowが「そのtokenをsampleする直前の状態」であることを解析時に明記する。

### 4.2 なぜ layer を細かく取る必要があるか

- 3層だけでは `F_l` の局所的なlayer updateを識別できない。
- layer制約を検証するpilotでは、まず全layer出力を取得する。
- `F_l` を機構的に分解するなら、layer出力だけでなく、少数pilotで次のcaptureも検討する。
  - block入力
  - attention出力
  - MLP出力
  - residual加算後
  - 必要なら attention entropy / KV 関連量
- capture位置を固定すれば、概念的には次を検証できる。

  ```text
  Delta_l h = Delta_l h_attention + Delta_l h_MLP
  ```

### 4.3 二段構えの取得案

1. 機構解析用 dataset:
   - generated `token:1 x all layers`
   - 各代表条件 / outcome 3-5 trials のpilot
   - `F_l`、layer update、event直前直後を調べる
2. 統計解析用 dataset:
   - generated `token:1 x pilotで選んだlayers`
   - 各主要条件20-50 trials
   - 成功 / 失敗、`N`、`min_moves` による分布差と予測性能を検証する

今回と同程度の782 generated tokens、約48 layers、5120次元、float16をすべて保存すると、圧縮前は概算で約384 MB/trialとなる。全layerをいきなり大量取得せず、all-layer pilotで必要な層と中間量を決めてからtrial数を増やす。

### 4.4 比較設計

- 同じ / 近い `min_moves` で `N` を変える。
- 同じ `N` で `min_moves` を変える。
- 同じ `N` / `min_moves` 内で複数 initial state とsampling trialを取る。
- success / final fail / search fail / loop trap / budget censoringを分ける。
- reasoning中の全Move mention軌道とfinal answerの実行軌道を分離し、final開始時には初期状態から評価し直す。

   - Question: layer制約とevent-scale token dynamicsを識別できるデータになっているか。
   - capture対象: generated区間、全layer、必要ならblock内部量。

## 6. 未解決の論点・注意

- full hiddenのcapture位置がTransformer blockのどこかを、runner実装で厳密に確認する必要がある。
- `h[t,l]` 単独では非Markovである。将来の予測モデルでKV cacheを直接保存するか、history embedding / delay coordinatesで有効状態を作るかは未決定。
- layer間raw hiddenは、表現基底やnormが層ごとに異なる。raw差分、正規化差分、translator後差分のどれを `F_l` の対象にするかpilotで判断する。
- Move eventは単一tokenではなくspanとして定義する必要がある。event前、event中、event後の窓を固定する。
- 現在のevent replayはreasoning中の全mentionを連続実行しており、final answer開始時に初期状態へリセットしていない。final評価用trajectoryを別に作る。
- 現在のsuccess runは完全な `</final>` blockを持たず、`boundary_ok=false`。final boundaryの機械的な確定方法が必要。
- PCAは引き続き可視化・診断に限定する。方程式を考える段階では元のhiddenまたは層別に十分な次元を使う。
